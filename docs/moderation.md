# Reporting, support and moderation

Implemented: signed-in players can send game/player reports or general support requests and view their own latest 50 cases. Game cards and social/blocked-account rows prefill reporting targets. Requests accept a category and 10–2000 character message, reject unknown fields, require exact application Origin, and are limited to 10 per account per hour in the single-instance service. Draft games cannot be probed through reports. Reports do not automatically penalize their target.

Verified current administrators have a moderator workspace with pending build previews, approve/reject decisions, open cases, targeted suspension controls, and resolve/dismiss actions. Every mutation rechecks the current administrator role, verified email and suspension state. Review and case decisions append history atomically with status changes; a second concurrent decision receives a conflict. Case resolution requires both an internal reason and a distinct public reply. Player responses project only public fields; moderator IDs and internal notes are excluded.

Build approval permits the creator to publish; approval itself does not publish a game. Case closure does not imply suspension. The moderator must separately inspect evidence and explicitly suspend a reported game/account when appropriate. Suspensions invalidate game access and account sessions as applicable. The UI asks for confirmation before a suspension.

Local evidence September 21: tests cover authentication/role/Origin checks, reporter isolation, private-draft rejection, strict input bounds, concurrent resolution, internal-note privacy, build reviews and suspension behavior. Full local suite: 29 passed. Real browser sessions verified report creation → moderator queue → resolve → reporter history/public reply; the reporter page did not contain the internal test note. These tests used disposable data, not a real abuse report.

Still required before launch: production administrator provisioning and access review; escalation/appeal procedures (including a route for suspended/logged-out users); support response expectations and staffing; detailed creator content rules; teen-specific safety review; evidence retention/deletion policies; appropriate legal review of copyright, privacy and abuse-handling obligations; queue pagination/assignment and operational alerting; financial reconciliation tooling. This implementation is not a substitute for an operated trust-and-safety program. No automated promise of immediate intervention is made.
