# Stripe event intake — test-only foundation

Implemented September 27, 2026. This is not subscription checkout, a financial ledger, paid entitlement fulfillment, advertising revenue or a creator payout system. Those remain required parts of the delivery goal. No Stripe account was connected and no provider API request or charge was made during local verification.

## Configuration and boundary

`PAYMENTS_MODE=disabled` is the default. `test` requires `STRIPE_SECRET_KEY=sk_test_…` and `STRIPE_WEBHOOK_SECRET=whsec_…`; `live`, live keys and incomplete test configuration fail startup. The snapshot-event API version is pinned to `2026-08-26.dahlia`, matching the installed Stripe SDK's generated version at implementation time. Set the provider event destination to that exact version; upgrades require fixtures and a deliberate code change. Secrets belong only in server environment settings, never a game package or repository.

The one `POST /api/payments/webhook` endpoint is mounted before browser Origin enforcement and JSON parsing. It accepts at most 256 KB of uncompressed JSON, verifies the SDK signature/timestamp against the exact bytes, and rejects live events, organization contexts, wrong versions and malformed identifiers. This Origin exception does not apply to other API routes. All responses are no-store; malformed signatures get 400, unavailable intake/storage gets 503. A 200 means either durable receipt/duplicate receipt or an explicitly ignored event type, not successful fulfillment.

Signed supported events are stored in `stripeEvents` under a deterministic test-mode/account/event key. Concurrent/repeated deliveries cannot add a second record or reset completion. Only event/object identifiers, scope, type, provider creation time and processing metadata are stored. No raw customer, card, address, invoice or payment payload is retained in this inbox. Incoming types without installed handlers remain visibly `awaiting_handler` rather than falsely completed. There are currently **no financial handlers installed in the application** and no automatic financial worker is started.

## Worker contract

`createStripeEvents({db, config, handlers, provider?})` exposes `drain({limit})`. The provider injection exists for deterministic local contract tests; normal construction uses the Stripe SDK. Each handler is keyed by event type and receives `{event, eventKey, isCurrent}`. Install only handlers that have passed their financial/authorization tests. New handlers make previously waiting entries eligible for processing.

Workers atomically lease entries for two minutes and retrieve the canonical event using server credentials and its connected-account scope, checking mode/version/type/object/scope again. The worker retries failures with 30-second exponential backoff, capped at one hour, for up to eight attempts. Expired leases are recoverable; a crash on the final attempt becomes `failed`. Ownership is checked before dispatch and acknowledgment, so an old worker cannot mark a newer lease completed. Provider errors are replaced by bounded failure codes, not logged or returned with secret-bearing messages.

This is at-least-once processing. A process can crash after a financial effect but before acknowledgment, and a handler can outlive a lease. Every financial handler must use `eventKey` plus its underlying business-object identity for idempotency, and use database transactions/conditional writes to atomically record ledger effects and relevant state. `isCurrent` is a preflight aid, not a transaction or fencing guarantee. Different events about the same invoice/subscription can also arrive out of order; handlers must reconcile current provider state and serialize/fence per business object. This inbox alone does not solve those problems. Future handlers must bound execution time and honor cancellation before enabling a periodic worker.

`GET /api/admin/payment-events` provides verified current administrators with counts and the latest 50 minimal status records. It excludes account mappings, leases and provider payloads. It is a diagnostic API, not yet a finance dashboard. Failed entries are retained for operator investigation; no blind public retry or deletion endpoint exists. Design audited replay and data-retention policies before launch. Stripe's event-retrieval window is finite; prompt incident response and reconciliation against durable financial objects are still required.

## Evidence and remaining gates

Local tests use real disposable MongoDB and the real Stripe SDK's signing/verification implementation, with a fake canonical-event retrieval adapter. They verify tampering/stale signatures/mode/version rejection, durable deduplication, concurrent leases, canonical scope checks, recovery, failure exhaustion, stale acknowledgments, raw-body integration and preservation of browser CSRF protection. These are **not Stripe sandbox end-to-end tests**. The application still advertises subscriptions and ads as unavailable.

Next integration work includes provider-supported connected-account onboarding, server-owned reviewed plans and commission snapshots, hosted checkout/management, verified entitlements, transactional ledger and refund/dispute/transfer reconciliation, creator/admin interfaces, SDK monetization calls, failure/cancellation/replay tests and actual sandbox verification. Live activation remains gated on owner fee/cost approval, account/business/tax eligibility, age-appropriate purchase policy, security review and proven financial reconciliation. No earnings guarantees.

A separate [test-only ledger foundation](ledger.md) now provides balanced append-only journals and read-only reconciliation primitives. It is not yet connected to this inbox or a payment provider and does not complete the financial integration requirements above.
