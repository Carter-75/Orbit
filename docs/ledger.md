# Internal accounting foundation — test mode only

This module is not a wallet, payout engine, tax system, creator earnings statement or proof of actual payment. It is an internal append-only journal for future verified payment handlers and reconciliation. No browser/game route can post entries; no financial handler currently uses it. Live mode is rejected and posting is disabled by default. No commission or fee policy has been approved or activated.

## Invariants

- Each journal contains 2–20 unique account lines, one lowercase three-letter currency code and nonzero integer signed minor-unit amounts bounded to one trillion per line. The lines must sum exactly to zero, checked with BigInt. Positive and negative mean debit/credit accounting direction, not spendable positive/negative user balance. Currency codes are syntactically validated; an eventual provider adapter must also verify that a currency is supported for the selected account/product.
- All lines are inserted atomically as one MongoDB document with majority write acknowledgment. There is no module update or delete operation. An error cannot persist only part of a journal. Entitlements or other documents are not part of this write; future cross-document financial fulfillment still requires a transaction or a rigorously tested durable state machine.
- Identity comes from test mode plus provider, account scope, business-object ID and accounting purpose—not webhook delivery ID. Repeated delivery of the same underlying business operation cannot create another journal. Canonical field/line ordering makes equivalent inputs idempotent; changed currency, amounts or policy snapshots for an existing identity produce a conflict for investigation, never overwrite the original. Separate purposes intentionally represent distinct accounting operations and require correct business rules in the future adapters.
- Optional policy version, basis-point commission and creator/project references are immutable snapshots supplied by trusted server code, not a browser. Test fixtures containing a 10% example are test data, not the platform's agreed commercial terms.
- A full accounting reversal appends inverse entries under a deterministic identity, with one reversal per original enforced by an index. It retains the original and its policy snapshot. It does not execute a provider refund, transfer reversal or payout. Partial refunds, tax adjustments, dispute reserves and payout eligibility require separate verified business handlers; this operation must not be substituted for them.
- Trial balances group currencies separately and use Decimal128 aggregation plus exact BigInt conversion; outputs are decimal strings of minor units. A regression test sums 9,100 journals beyond JavaScript's safe integer aggregate range. Reports are bounded to 10,000 account/currency rows and five seconds; larger workloads must be partitioned rather than truncated silently. These are diagnostics, not measured production capacity.

## Stripe balance-transaction mapping

`stripeBalanceJournal({transaction, scope})` converts a **server-retrieved, provenance-checked test** BalanceTransaction into three unallocated accounting lines: actual processor net balance movement, actual fee, and opposite gross in an unallocated control account. It verifies `gross - fee = net`, supports negative movement/fee directions, drops zero lines and explicitly rejects zero-effect records for separate classification. It discards unrelated provider fields. It does not estimate fees, calculate creator revenue or assume that processor funds are available for withdrawal.

The converter is pure and does not authenticate its input. The future calling adapter must retrieve from Stripe using the configured test key and correct account scope, validate ownership, and never accept browser-supplied transaction objects. Stripe BalanceTransaction itself has no test/live flag used here; stamping untrusted input as test is not provider verification. `compare` checks an expected journal against the stored fingerprint and returns missing/matched/mismatch plus whether it was reversed. It makes no changes. This is a building block for reconciliation, not a completed account-wide reconciliation process.

## Operator access and remaining controls

`GET /api/admin/payment-ledger` requires a current verified, unsuspended administrator and returns the test trial balance plus the latest 50 explicitly projected journals. Configured disabled/test mode and a non-withdrawable-total notice accompany the response. There is no HTTP posting, reversal, cash-out or export endpoint. Frontend finance dashboards are still required.

The application contract is append-only; it is not tamper-proof against a database administrator. Before launch, scope database roles, protect backups, establish retention and access auditing, prove restore/reconciliation procedures, and implement migration/integrity checking. Review the chart of accounts and provider-specific flow with an appropriate accounting professional. Reconciliation must cover every relevant provider account, transaction, currency and time window with explicit completeness checks, not just matching one fixture.
